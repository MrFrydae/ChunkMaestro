# Proposed threat model and abuse-case acceptance

Source: [authoritative answers](../product/requirements-source.md), especially Q14, Q17–20, Q25, Q31, Q51–68, Q94–104, Q157, Q163–175, Q196, Q204. See [ADRs](../architecture/README.md) for alternatives and recovery designs. Status: **proposed; no mitigation implemented or penetration test executed at bootstrap**. This model supplies future acceptance obligations; a green specification checker proves only document integrity.

## Assets, actors and trust boundaries

Protect production worlds/configuration, approved deployment/schedule intent, durable outcomes, recovery sets and encryption keys, controller/agent trust keys, SSH/RCON/provider credentials, personal player/log data and truthful operational state. Loss of Minecraft data and undetected unauthorized root execution have highest impact; backups and migration need availability as well as secrecy.

The local desktop owner is the initial authorized operator, tied to OS identity; there are no moderator accounts yet. A stolen session or malicious local process may invoke exposed services or read staging/SQLite. An OS administrator or compromised desktop root can subvert local storage, key use and audit history; this design does not promise immunity against that actor. The application CA is not globally trusted. SQLite hash chains detect some tampering but do not make local evidence immutable against an OS attacker.

On Linux distinguish restricted `minecraft-agent`, unprivileged `minecraft`, root-owned helper/policy/package maintainer, other local users and adjacent instances. The Minecraft JVM executes downloaded plugins/mods; a hostile plugin can intentionally execute arbitrary code **as the Minecraft user**, read/write allowed game files and falsify game telemetry. A compromised agent can misuse its already granted service/file/schedule authority; helper validation must still prevent root escalation and cross-instance actions. Linux root compromise defeats local enforcement and needs host rebuild/re-enrollment rather than trusting agent reports.

Remote actors include LAN/VPN attackers (the LAN is not inherently trusted), counterfeit agents/controllers, hostile SSH endpoint/MITM, malicious archive/catalog/Git authors, provider/API/probe operators, extension publishers, optional external AI/notification services and untrusted PR contributors. A signed artifact identifies provenance only; it is not proof that code is benign. An enrolled external probe supplies location-scoped observations, not global outage authority.

Boundary flow: native Avalonia UI → core authorization → local SQLite and OS secret stores; core → agent-facing LAN/VPN mTLS listener ← outbound Linux agent; agent → durable local journal/scheduler → authenticated root-owned helper; agent → permitted Minecraft roots/private RCON/bridge/JVM. External provider and extension IPC grants are separate. Desktop staging → approved immutable plan → safe-root writes; host-consistent backup → encrypted bounded local/NAS store → verified off-host transfer. Crossing each boundary requires its own identity, target scope, fresh prerequisites and audit record. UI hiding alone enforces nothing.

## Security acceptance and residual decisions

Prioritize helper/root escape, enrollment takeover, data loss/restore integrity, arbitrary extension access and reconnect duplicate disruption before live feature enablement. High-risk implementation requires functional, security/reliability and UX/accessibility/performance independent verdicts; this document supplies none. Safety modules need ≥90% line, ≥85% branch and ≥80% applicable mutation, plus real denial and recovery evidence; percentages cannot replace threat-case testing.

[OD-04](../product/open-decisions.md#od-04-backup-destination-quotas-and-recoverable-keys), [OD-05](../product/open-decisions.md#od-05-schedule-civil-time-locking-and-interruption), [OD-06](../product/open-decisions.md#od-06-listener-and-secure-ownership-handoff) and [OD-11](../product/open-decisions.md#od-11-enforceable-extension-confinement) block their dependent safety claims. Root-helper IPC choice, certificate validity/rotation window, schedule approval lifetime and exact sandbox mechanisms remain proposed implementation selections requiring evidence. Do not solve a failure by widening privileges, silently downgrading transport, exposing public ports, replaying disruption or overwriting worlds.

No credentials, private keys, new permissions, live host access or paid services are required for this specification. Docs-only signed revert is the recovery for this PR. Future incidents must retain sanitized operation IDs/timestamps/results, contain credentials/trust, protect recovery points and distinguish observed facts from unknown outcomes.
